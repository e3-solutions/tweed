# Anonymous code review and supplemental counterexample

Three fresh Codex reviewer contexts each inspected two complete task groups, covering all 48 candidates once. They received requirements, baseline code, full production source and exact patches with assignment, model, arm, oracle and completion metadata removed. Source style could still offer clues; metadata blinding was an instruction and packet boundary, not operating-system confinement. Empty and incomplete output remained included. Original anonymous reports were preserved; assignment labels were added only after all three reviewers finished.

[The review index](quality-results/index.json) links three complete reports, with source and patch hashes, finding locations, quoted code, observable consequences, suggested repairs and uncertainties. The reports contain 27, 33 and 31 static findings. These counts are not calibrated code-quality scores: task groups, inherited defects and reviewer granularity differ. A source-traced finding is still a reviewer judgment, and the proposed counterexamples were not executed by these reviewers. There was one reviewer per candidate, not repeated independent judgments of each output.

Findings concern concrete requirements: child ownership and teardown during resume/failure, coordinator turn identity, implicit installation and invalid release snapshots, incomplete review selection, invalid budgets, and unusable continuation tokens after a changed Git identity. The reports distinguish inherited baseline behavior and implementation-introduced defects where their source traces support that distinction. They do not manufacture an abstraction complaint merely because code is long. Suggested repairs describe work remaining; their implementation time has not been measured.

A supplemental attempt to reproduce the release-marker symlink finding was blocked by an automated safety check for possible cybersecurity risk. It was not executed or counted as behavioral proof. That finding remains a static observation with a proposed counterexample.

## Executed supplemental routing probe

After the static review, the owner exercised all eight PR32 candidate sources through their public `run_phase` function using the original deterministic native-process fixture. No model, network or live app-server call occurred. After a soft-budget steer acknowledgment, a command-start event from the coordinator's **old** turn arrived, followed by the active turn's valid continuation receipt. The old-turn event must not determine the active outcome.

Six candidates rejected the valid continuation because the stale event set their `post_steer_work` guard. Both requested-Astra candidates accepted it. A paired control sent command-start work from the **active** turn: all eight correctly rejected that work. Every fixture process was closed. [Exact results and source hashes](quality-results/posthoc-routing.json) bind sixteen observations to the reviewed source files; the [probe script](posthoc_routing_probe.py) is provided.

The first diagnostic incorrectly supplied a completed receipt after a steer, which violates the existing continuation contract. Its results are retained privately as invalid diagnostic evidence. The final probe supplies the required `needs-input` continuation, canonical question and unverified-obligation summary, and adds the active-work control. It is a post-hoc requirement check, not a preregistered model score. No primary grades or worker attempts were replaced.

This demonstrates that the registered selected oracle missed a consequential routing case, including in some artifacts it accepted. It supports retaining independent source review and targeted counterexamples alongside execution tests. It does not establish a general Astra-versus-Opus ranking or quantify broad code consistency. The single maintenance extension is a separate measure of change outcomes and observed work, with initially correct, incorrect and unknown sources kept separate.
