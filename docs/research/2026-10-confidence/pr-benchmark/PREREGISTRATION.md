# Real pull-request comparison: preregistration

Registered design date: 2026-10-12. This document and [protocol.json](protocol.json) freeze the hypotheses, seven intervention arms, resource envelope, selection rules, outcomes and analysis **before solver outcomes**. This is a design registration, not a results report. Before execution, the owner must seal the selected task manifest, exact trial queue, package/runner hashes and identical budget-allocation policy in a separate registration receipt. Any result-driven change requires a dated amendment and a separately labeled experiment.

## Question and seven arms

Does the proposed protocol or one of five distinct workflow overlays improve real PR task correctness, truthful completion or autonomous progress compared with the exact original Confidence Protocol under the same model and resources?

| Arm | Exact toolkit | Intervention | Falsifiable hypothesis |
| --- | --- | --- | --- |
| Original CP 0.5 | `57adc49283931f6b617378e8cf924d700528cba3` | Exact shipped skill, references, assets and executable toolkit; no added overlay | Historical comparison baseline, including its existing review instructions. |
| Current CP 0.6 | `9f3afa68381a510a9d060acb4b8f8bec05888e27` | Exact current package; no overlay | Durable obligations and review provenance prevent omitted or falsely completed proof. |
| Compact routing | Current CP 0.6 | Load task-relevant references and keep proof context concise | Lower overhead preserves or improves held-out correctness. |
| Counterexample first | Current CP 0.6 | Reproduce and challenge behavior before implementing the causal fix | Early disproof improves boundary and preservation correctness. |
| Dependency slicing | Current CP 0.6 | Minimal end-to-end slices and explicit meaningful prerequisites | Dependency state reduces missed integration work and early stopping. |
| Independent review | Current CP 0.6 | Fresh scoped proof design and post-change adversarial challenge | Counterexample discovery offsets review's shared-budget cost. |
| Bounded repair | Current CP 0.6 | Durable progress packet and an explicit no-progress rule | Better recovery and less stalled work without false completion. |

The exact overlay text is in the JSON. These are complete workflow variants, not claims that every difference isolates one causal instruction. Current versus original combines instruction and executable-toolkit changes. The five overlays compare additional workflow direction while retaining the same current package. Every arm has the same reviewer capability; the original is allowed to use its existing Critical review procedure. Neither reviewers nor tools are withheld to favor the review intervention.

The baseline is not a summary. Materialize each package from `git archive --format=tar` at its pinned revision, honoring release exclusions, and verify its archive, skill and executable hashes from the JSON. Supply `SKILL.md` verbatim in the same prompt position and mount the full shipped references, assets and scripts read-only. Relative references resolve in that arm's package. ## Tasks, held-out tests and access separation

Target six real merged Tweed PRs, provisionally #32, #31, #40, #34, #39 and #35 in that selection order. The curator uses deterministic standard-library cases with substantive behavior changes. Every candidate must demonstrate that its sealed selected regression checks fail on the PR base and pass on its head under the identical grading environment. This is an oracle control, not a solver result or proof that the oracle covers every requirement.

The first three candidates are the prespecified fallback set. Use three only if all three controls qualify and one or more remaining candidates cannot be curated under the allowed environment. Decide and record six versus three before the first solver run. If the first three do not qualify, stop for honest curation rather than selecting a favorable subset. Do not replace a task because any arm struggled with it. Preserve curation failures and reasons.

The manifest records exact base/head SHA, source snapshot hashes, plain behavioral requirements, allowed production paths, base-visible tests and exact visible-test commands, dependency/runtime state, selected held-out tests and fixtures, and sanitization operations. Only the parent grader may read head solution, PR body/diff/history or held-out oracle. Solvers receive sanitized base source and base-visible checks, without original history/remotes or agent-autoload files. Product workflow files remain. The sandbox must also confine child test code; hiding paths in a tool description is insufficient. No oracle/head location may leak through the solver's configuration, environment or tools.

A fresh single-commit synthetic Git repository is permitted for CP source binding. It does not contain the original history or head solution. Each trial gets a fresh base copy, context and evidence. A reviewer sees only that trial's requirements, current source, assigned question and visible proof. It receives no proposed verdict, hidden reasoning, gold output or other-arm result.

## Model, tools and aggregate budgets

Use `claude-opus-5-5`, explicitly `medium` effort, for main solver, optional fresh reviewers, continuations and any terminal assessment. Do not configure a fallback. Record the actual observed models, requested effort, refusals and usage; flag a mismatch rather than treating it as the requested-model comparison.

Every arm receives the same confined MCP tools: `list_files`, `read_file`, `replace_text`, `write_file`, `run_tests`, `confidence`, `request_review`. Native solver tools are disabled. The manifest suggests visible-test commands; the shared tool accepts Python, Git and non-login Bash/Sh commands for local reproduction and new tests under OS confinement. It blocks network and reads outside the workspace, including hidden tests. The protocol package is immutable. Reviews have the same source/test access with read-only source tools and subprocess restrictions, and no recursive reviews. The grader restores original visible tests and sealed acceptance tests independently. These common adaptations make this a fixed-harness comparison, not a claim about unmodified vendor harnesses.

Each trial has a **$4 nominal aggregate list-price stop threshold and 600 seconds total wall-clock budget**, including main calls, continuations, reviewers, helpers and terminal completion collection. A model stage may run at most 240 seconds. Operational stages share $3.75 and 570 seconds: the initial main episode has a $1.75 threshold and at most two fresh reviews have $1 each. If the initial completion is false or unknown, known unused operational budget and time may fund one common continuation, capped at 240 seconds and the remaining pool after reserving one dollar for each unused review slot. Refuse a continuation if any prior cost is unknown. It retains the same workspace and replays the visible main messages and tool results, excluding hidden reasoning; it receives no hidden grading, altered task or human hint. Reviews stay available within their reserve. This allocation rule is identical for all arms and may leave budget unused when reviews are declined. No stage gets a new $4 allowance.

The final 30 seconds are reserved for collecting/persisting the last valid structured model completion declaration, with a $0.25 reserve. The collector makes **no additional model call** and performs no operational tool call, grading or task repair. A missing/truncated declaration remains null. The monetary reserve is not released after the operational deadline. CLI currency thresholds can overshoot on an in-flight API response; stop at the first observed crossing and retain actual cost plus operational/aggregate over-budget flags instead of claiming a perfectly hard currency cap.

These are nominal resource bounds, not spending or runtime forecasts: the 84-trial nominal envelope is $336 list-price usage and fourteen serial deadline hours, with any in-flight monetary overshoot disclosed. Three concurrent fresh workspaces shorten elapsed time without sharing outcomes. Actual subscription charges are not inferred from list-price estimates. Budget/time exhaustion, unavailable review or a denied tool remain observable results and cannot be retried until success.

## Repetition, order and terminal collection

Run six tasks × seven arms × two independent contexts = **84 planned trials**; the prespecified three-task fallback is 42. Use the frozen scheduling algorithm in the JSON: a deterministic task shuffle, rotated arm order, and a reversed second-repeat order. Save the exact queue before running and permit at most three concurrent tuples. The scheduling seed does not make model generation deterministic or create 84 statistically independent tasks.

A trial's final report is the same structured object for every arm: `complete` boolean, `summary` string, `remaining` string list. `complete=true` declares that the requested behavior and required protocol proof are complete based on visible evidence. Hidden tests are run only after the final workspace is sealed. The grader does not infer correctness from the declaration, nor infer `complete=false` from missing/truncated output. The terminal collector cannot restart task execution.

Preserve every attempt. One infrastructure retry is allowed only for a proven pre-solver setup failure or a transport failure before any assistant response, with the identical configuration and a fresh workspace. Model refusal, denial, unsuccessful patch, budget exhaustion, failed oracle or missing final output is not infrastructure flakiness. A necessary configuration repair after substantive outcomes starts a dated separate experiment and retains the original results.

## Outcomes and analysis

Primary correctness is binary: the submitted production tree passes all sealed required acceptance/preservation checks and code-scope, dependency and test-integrity rules. Solver-authored tests and CP validation do not replace the held-out oracle. Report oracle correctness independently of the solver's completion declaration; a correct patch with incomplete proof can be correct while honestly partial.

False completion is `complete=true` with held-out correctness false. Report its numerator divided by all scored trials and, separately, by trials declaring complete; disclose both denominators. Missing terminal declarations are null and reported separately. Truthful success additionally requires correctness, declared complete, empty remaining and no unresolved required proof in submitted evidence.

Autonomy metrics include guard denials, out-of-envelope attempts, required human interventions, optional review requests, stages, no-progress stops, blockers and budget/time exhaustion. A human intervention means external task-specific help, a changed requirement, a suggested solution or manual workspace repair during a trial. Mechanical execution of the frozen policy, routine registration and automated review are not interventions. Humans must not review task answers or offer hints during solver execution. Efficiency includes aggregate wall time, model/tool/test breakdown, all token categories and cost including review/terminal calls. Preserve infrastructure invalidity, model mismatch, contamination and outcome failures separately. An attempted forbidden action stopped by a working guard remains a scored denial, not an invalid experiment.

All scheduled task-arm-repeat tuples remain in the assigned intention-to-treat denominator, including incomplete and harness-invalid runs. Only an observed valid held-out pass contributes to the primary verified-success numerator; unavailable grading is unverified, not a fabricated observed oracle failure. False completion requires an observed failed oracle, so ungraded completion claims remain unknown. Report known-graded/model-conforming sensitivity analyses separately, with their reduced denominators. Preserve unknown cost, terminal completion and intervention status rather than filling them with zero.

The paired unit is the **task**. Average the two repeats in each task-arm cell, compute each of six alternatives minus the original on that task, and publish all paired differences and the overall paired mean. Do not treat repeated trials as independent samples. Enumerate every ordered whole-task bootstrap resample, retaining both repeats of each sampled task, and select descriptive 95% inverse-empirical-CDF percentile intervals: 6^6 = 46,656 resamples, or 3^3 = 27 under fallback. Use quantile rank `max(0, ceil(q*N)-1)` at q=0.025 and 0.975. Exact enumeration removes Monte Carlo sampling error, not selection uncertainty. Publish paired wins/losses/ties. Small-sample bootstrap intervals are unstable; these intervals are descriptive, not a significance test. No inferential p-values or significance-based winner are prespecified. Report all six planned baseline contrasts rather than selecting a favorable one.

Publish every task-arm-repeat result with denominators, failures, missing terminal replies, resource use and invalidity reasons. Alternative-versus-alternative rankings, cost-adjusted rankings and subgroup analyses are exploratory. No arm, prompt, oracle, scoring rule or exclusion may be tuned from these outcomes.

This purposive single-repository comparison has only six tasks and two repeats, one model/effort/harness and a local oracle. It cannot establish population-wide accuracy, arbitrary complex-project autonomy, production persistence correctness or transfer to Sol/Astra/Codex/T3. Public code can also be known to a model. Report these limits even if one arm wins every selected task.

## Evidence and source rationale

The alternatives are motivated by the completed [model/harness research](../models-and-claude.md), [project patterns](../harnesses-and-projects.md), and [independent protocol analysis](../protocol-analysis.md). They remain hypotheses. Incremental prompt ablation is supported by the [GPT-6 guide](https://developers.openai.com/api/docs/guides/latest-model); separating transcript claims from environment outcomes and repeating agent trials is supported by [Anthropic's agent evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Durable progress state addresses the bounded handoff failure mechanisms in [long-running harness research](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), whose original web-app setting limits transfer.

Before the first trial preserve: this protocol hash, selected manifest hash, package inventories/hashes, runner/runtime version, sandbox/tool schemas, stage allocation, exact queue and curation control receipts. Afterward preserve: main/review/terminal output, actual model usage, tool and denial events, final source digest, submitted production diff, visible checks, sealed held-out result and grading reason. Keep held-out material outside solver access and publish only authorized redacted evidence. This preregistration contains no solver outcomes.
