# Harnesses and project patterns for Confidence Protocol

Research date: 2026-10-12 (America/Toronto). This document separates observed upstream behavior, proposed adaptations, and proof still needed. A model generates decisions; a harness owns tool execution, permissions, state, concurrency, and recovery. None of the projects reviewed makes a model's self-reported confidence a correctness certificate.

## Codex: integrate the lifecycle, then judge the outcome

The official app-server contract specifies a per-connection `initialize` request followed by `initialized`, version-specific schema generation, and a thread/turn/item lifecycle. `turn/completed` can describe interruption; reading the final status matters. `thread/compact/start` acknowledges immediately while progress arrives later. Stable and experimental surfaces differ; experimental WebSocket transport is currently unsupported for production. Build against schemas generated by the installed CLI, not a hardcoded guessed protocol. [Official app-server documentation](https://learn.chatgpt.com/docs/app-server).

The reviewed source declares `Completed`, `Interrupted`, `Failed`, and `InProgress` turn statuses. It also documents that live settings changes do not rewrite already captured pending approvals. A successful transport connection, accepted turn, tool result, and completed turn therefore answer different questions. [Pinned turn protocol](https://github.com/openai/codex/blob/a9b0815167c27ab13719dd12d13b63e02b70d221/codex-rs/app-server-protocol/src/protocol/v2/turn.rs).

Codex subagents keep noisy exploration out of the main decision context; documented defaults inherit the parent's model and reasoning unless configured otherwise. Parallel reading is a safer initial fit than overlapping edits. Each agent still consumes model/tool work; agent count does not measure independence or quality. [Official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents).

**CP adaptation:** a durable report remains authoritative across context compaction. On resumption, reread the contract and report, inspect available receipts, compare source identity, and recompute readiness. A runtime terminal status is a necessary run condition when delegating through that runtime; it cannot substitute for obligation proof. Keep provider status, evidence validity, and completion judgment separate.

**Counterexample:** replay a receipt whose provider turn was interrupted but whose text says “all tests passed.” It must not support completion. Repeat for an acknowledged compaction without a terminal completion event. A change in permission settings must not imply retroactive authorization for a queued action.

**Compatibility limit:** the existing CP command runner is not a Codex app-server client. Documentation about app-server behavior establishes what an adapter would need; it does not prove a direct CP integration exists.

## T3 Code: normalize capabilities and preserve execution ownership

The user's “t3code” resolves to the current public [`pingdotgg/t3code`](https://github.com/pingdotgg/t3code/blob/48595c787cf5ffe3fcc089ce36754d7c601e4007/README.md). Its README describes an agent harness control surface over locally installed providers, with web/mobile/Electron clients. It is not a replacement inference model.

Current code moved beyond search-index results: `apps/server/src/provider/Services/ProviderAdapter.ts` returned 404 at the reviewed SHA. The relevant boundary is now `packages/provider-core/src/server/ProviderAdapter.ts` and orchestration is under `apps/server/src/orchestration-v2`. The current adapter distinguishes session status from terminal turn events, separates failed turns with failure/retry information, and makes capabilities discoverable through `getCapabilities()`. It probes background work per native thread so siblings cannot keep an unrelated root subscription open. [Pinned adapter source](https://github.com/pingdotgg/t3code/blob/48595c787cf5ffe3fcc089ce36754d7c601e4007/packages/provider-core/src/server/ProviderAdapter.ts).

T3's architecture records intent before external effects, commits command receipts and outbox effects with state, and recognizes that command acknowledgement is not effect completion. Provider termination and checkpoint finalization are separate milestones. Clients cannot replace the server's workspace, credentials, or machine state. Tests drain queued and currently executing work. [Pinned architecture](https://github.com/pingdotgg/t3code/blob/48595c787cf5ffe3fcc089ce36754d7c601e4007/docs/internals/overview.md).

Workspace rollback safety canonicalizes paths and rejects overlapping/shared workspaces, including archived threads and live errored provider sessions. The check runs at command admission and again before provider rollback. [Pinned restore safety](https://github.com/pingdotgg/t3code/blob/48595c787cf5ffe3fcc089ce36754d7c601e4007/apps/server/src/orchestration-v2/CheckpointRestoreSafety.ts).

**CP adaptation:** retain canonical checkout identity on captured proof. A read-only `next` command can derive dependency readiness from validated durable state; it should not execute the suggested verification string. Default unknown provider features to unsupported. Preserve model/harness identity on independent reviews without claiming that a different model is automatically an independent oracle. Completion should wait for proof capture/finalization, not an empty task queue or elapsed time.

**Counterexamples:** copy an otherwise identical report to another checkout; continue validating its recorded original roots and label them, rather than presenting proof as belonging to the caller. Replace a worktree path with a symlink to an overlapping checkout; canonical scope must still detect the overlap. Complete one native thread while another has background work; the first's status must remain independent. None of these require CP to implement T3's complete event-sourced system.

**Rejected:** importing T3's orchestration database, hidden Git checkpoint system, or remote RPC architecture into a small skill. These solve a larger application's problems and would create unnecessary compatibility and operational obligations.

## OpenHands: delegation is useful but shared state needs boundaries

The latest `OpenHands/OpenHands` README identifies Agent Canvas as a client using the canonical SDK/Agent Server API in `OpenHands/software-agent-sdk`. Old descriptions of the main repository as the entire runtime are stale. [Pinned Canvas README](https://github.com/OpenHands/OpenHands/blob/0f1b6f62507f1ccdb4e63f61cf3dc48356a0d4fa/README.md).

The SDK delegate executor creates typed child conversations, resets their model metrics, persists children when the parent persists, limits child count, and runs tasks concurrently. It shares the parent's workspace and distinguishes results from exceptions. Its default confirmation handling may continue a child when no custom handler exists. That exact code is a runtime behavior, not a CP authorization recommendation. [Pinned delegate executor](https://github.com/OpenHands/software-agent-sdk/blob/e3a26821f8f7c85e98078c7b5e1a80647fc7d0c7/openhands-tools/openhands/tools/delegate/impl.py).

**CP adaptation:** assign bounded responsibility and a counterexample question to each reviewer. Give shared-workspace workers explicit file ownership; let read-only reviewers inspect the same snapshot. Preserve per-worker source/evidence references and failure states, then integrate results through one owner. A “no response” is missing proof, never assent. Record a distinct unavailable/partial result when permission, budget, or access blocks the reviewer.

**Counterexample:** one child fails while seven complete. Aggregate completion must still expose the failed role. Eight overlapping patch authors are not eight independent validators. Restrict research workers to read/research tools and keep external data exposure inside authorized scope.

**Rejected:** copying a permissive confirmation default or treating local delegation as isolation. Separate conversations do not provide separate filesystems, independent oracles, or distinct assumptions.

## Aider: concise context and a bounded repair loop

Aider's documented map includes important symbols and signatures, ranked within a context budget. It guides file discovery rather than proving behavior. [Repository-map documentation](https://aider.chat/docs/repomap.html). Its lint/test workflow can run after edits and react to nonzero exit codes; formatters can modify the source during verification. [Lint/test documentation](https://aider.chat/docs/usage/lint-test.html). The reviewed implementation caps reflection rounds and distinguishes automatic lint and test configuration. [Pinned coder source](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/coders/base_coder.py).

**CP adaptation:** keep a compact execution handoff with requirements, obligation dependencies, source identity, strongest raw receipts, unresolved assumptions, and the next discriminating test. Repair the concrete failing boundary before broadening the suite. Stop repeated identical repairs when they provide no information; change the hypothesis, reduce scope, or report the unresolved blocker. A formatter that changes source invalidates proof tied to the pre-format source.

**Counterexample:** run an always-green command after a defective change. It may prove the command ran, but cannot prove the contract. Generate a flaky pass after several failures and cite only the pass: retain the contradictory attempts when judging sufficiency.

**Rejected:** adding a repository-map implementation or token-ranking dependency to CP. The skill can use the host harness's existing exploration tools. Adding context summarization code would not repair its proof gate.

## LangGraph: durable state is different from exactly-once effects

The current `durable-execution` documentation URL redirects to Persistence. Checkpointers preserve thread state; stores preserve cross-thread application data. RAM-backed savers do not survive restart. [Persistence documentation](https://docs.langchain.com/oss/python/langgraph/persistence).

The checkpointer guide distinguishes pending task writes, full checkpoints, and replay. Replaying after a checkpoint re-executes later nodes, including APIs and model calls. `exit`, `async`, and `sync` durability have different crash windows; synchronously persisting a checkpoint does not itself make an external API transaction atomic. [Checkpointer documentation](https://docs.langchain.com/oss/python/langgraph/checkpointers). The pinned functional API demonstrates task results cached through the checkpointer and separate saved versus returned state. [Pinned functional API](https://github.com/langchain-ai/langgraph/blob/799c2f04fd3a56186e24e9fb8bbf3568e543cfbe/libs/langgraph/langgraph/func/__init__.py).

**CP adaptation:** preserve contract/report/run records as the recovery boundary. Describe whether a suggested step is read-only, replayable, or needs reconciliation after an unknown external outcome. Keep “operation intended,” “command executed,” and “result recorded” distinct. Reusing an immutable receipt requires valid integrity, source/environment freshness, and matching obligation scope; deduplicating a write requires a separate external idempotency contract.

**Counterexample:** process crashes after an external side effect but before the report writes. Resuming must reconcile the remote state rather than repeat the side effect. A orphan log without a complete receipt cannot become passing evidence. A replay can reuse still-current proof; it cannot make stale proof current by rewriting a status field.

**Rejected:** adopting LangGraph as a dependency, automatically replaying every proposed step, or promising exactly-once effects from local JSON durability.

## Inspect AI and SWE-bench: make the measurement instrument explicit

Inspect distinguishes model failure, scorer execution error, and an unscored result; these affect denominators differently. A failed grader is not a valid positive judgment. [Scoring policy](https://inspect.aisi.org.uk/scoring-policy.html). Its sandbox contract includes provider-specific limits; execution output may be truncated even when execution returns successfully. [Sandbox documentation](https://inspect.aisi.org.uk/sandboxing.html).

The reviewed SWE-bench grader separates failure-to-pass repairs from pass-to-pass regression protection. It rejects skipped repair tests, detects positive counts showing a suite actually ran, and cross-checks log claims against captured command exit status. Those defenses address concrete false positives, while remaining parser conventions have benchmark-specific limits. [Pinned grading source](https://github.com/SWE-bench/SWE-bench/blob/02e7a74ffd0b707aab73d203fe87bdc7c76afc8e/swebench/harness/grading.py).

**CP adaptation:** use literal public-behavior acceptance assertions, meaningful regressions, and a test oracle designed independently of the implementation. Preserve model/tool/harness/environment settings when measuring model changes. For a bug, run the unchanged oracle against the defective version and the fixed version when practical. When the oracle cannot run, leave the product claim partial even if report validation succeeds. Use targeted mutants to ask whether proof rejects the precise bug mechanism; surviving meaningful mutants reveal insufficient proof.

**Counterexamples:** tests that collect zero cases, required tests all skipped, a process that prints success but exits nonzero, a malformed grader verdict, and a killed run with incomplete output. Each must stay separate from valid contract success. A curated mutation suite measures those defenses only; it is not a general autonomous coding benchmark.

**Rejected:** model majority voting as a substitute for tests, score inflation by excluding inconvenient failures, claims of improved task success without matched controlled trials, or copying benchmark parser heuristics as a general test oracle.

## Proposed scope and evidence needed

The smallest coherent CP improvement is optional dependency metadata plus deterministic read-only next-step selection, structured review provenance, and explicit recovery guidance. These improve control of complex tasks without creating a second harness. They are design proposals until the PR's tests demonstrate them.

| Proposed rule | Discriminating proof |
| --- | --- |
| A dependent obligation cannot pass or become ready while its prerequisite is unproved | Missing/failed/excluded ancestor, dangling ID, self-cycle and two-node cycle fixtures |
| Next-step selection never executes report text | Verification string containing a sentinel-writing shell command; sentinel remains absent |
| Resumption derives status from durable validated artifacts | New process reads same report; mutate source/evidence and verify readiness/completion changes |
| Structured review belongs to a model, harness, role, scope and snapshot | Missing identity, stale snapshot and unsupported “independent” assertion are rejected or disclosed |
| Checkout-bound evidence keeps its original source scope | Copy contract/report/runs to a distinct checkout; retain original recorded scope and invalidate when that source changes |
| Terminal command failure cannot become product proof | Nonzero exit, timeout, signal and false success text cannot support a pass |
| A compatible baseline remains usable | Legacy flat contracts and Python 3.10-compatible syntax retain existing behavior |

The first batch's observations about cherry-picked captures, paired before/after oracles, and crash-orphan labeling are hypotheses about CP requiring executable reproduction. Their presence in a research-agent summary is not proof that the PR fixes them. Implementing every idea at once would make regressions harder to attribute; the PR should explicitly identify accepted, deferred, and rejected adaptations.

## Licensing and integration limits

This research borrows general patterns and test questions. It does not import upstream code. If implementation later copies code, preserve required notices and check the license of that exact file/subtree and its dependencies; repository-level badges are insufficient. Pins support reproducible review, not an assurance about vendor services or unpublished internal behavior. Protocol documentation and upstream tests are not evidence that every installed provider, account, platform, or preview feature supports the same path.

## Executable integration finding and regression coverage

A real CLI integration probe exposed a scope-relocation defect during this change: capture a passing run with unignored evidence under `source/.confidence`, copy that directory to another caller, then invoke `next` on the copy. The original implementation recomputed the original source fingerprint with the copied evidence directory as its exclusion. Previously generated evidence in the original checkout entered the source fingerprint, causing a false stale-source refusal despite unchanged source.

The fix records the original evidence-directory location in newly captured run records and reuses that location while validating source freshness. A copied report still names the original source root; it does not claim the caller's source is verified. The acceptance test requires a valid frontier after relocation, explicit original root/cwd in `source_scopes`, then refusal after modifying the original source. This is a concrete application of T3's execution-ownership boundary, implemented independently rather than copied from its code.

The new [CLI integration suite](../../../skills/confidence-protocol/tests/test_autonomy_integration.py) also exercises ordered progress through a three-node dependency chain, rejection of premature dependent passes, replacement of upstream support invalidating two downstream passes, idempotent retry, legacy flat contracts, cycles/dangling references, byte-preserving read-only planning, malicious verification text, nonzero commands printing forged success, and attributable-review self-identity/reference-integrity checks. These tests use real temporary Git repositories and fresh CLI subprocesses. Review identity/model/harness fields are declarations checked for shape and consistency; the validator does not authenticate a reviewer or independently attest model execution. The integration review fixture tests that declared provenance and reference integrity gate, rather than claiming an external reviewer ran inside the fixture. These tests prove these bounded behaviors; they do not measure overall model coding accuracy or external provider interoperability.

## Independent executable project-pattern probes

The project testing parent spawned eight actual native Opus 5.5 workers. Its first receipt reported only seven completed; a same-session continuation recovered their results without spawning new workers. That continuation has zero new-worker stats, so its prose that all eight finished is not an independent eighth completion counter. Seven workers executed substantive probes; the malicious-string role ran only CLI help because its heredoc probes were denied, and a replacement role completed with its own actual one-spawn/one-completion receipt. Empty parent `permission_denials` did not mean children had no denied calls.

The recovered results include a diamond dependency graph plus independent branch, a 60-node invalidation chain, 47 held-out acceptance checks, 49 scope probes, 17 restart/corruption cases, subprocess timeout/signal/log-limit controls, legacy round trips, and an independent mutation matrix. These are executed finite probes, not a claim about broad autonomous task success. Several initial expectations were corrected against the declared contract, rather than counted as product failures.

Nine mutation changes were tested against nine separate public-CLI oracles. Eight meaningful mutants were rejected: removing dependency status validation, making frontier ignore prerequisites, enabling telemetry in `next`, bypassing validation errors, removing the symlink guard, disabling source freshness, disabling downstream invalidation, and skipping review contract-digest validation. The ninth changed a redundant ancestor-validation call and survived because an earlier guard still enforced the same rule; it was equivalent for these oracles. A separate background attempt to run the repository's own suite against each mutant was killed and produced no usable result. We therefore claim the independent oracle matrix, not repository-suite mutation coverage.

The panel exposed inconsistent timeout metadata, an editable source-exclusion anchor, obsolete redacted support-bundle record handling, duplicated dependency diagnostics, and overly broad documentation claims about tampering. These findings need individual reproduction and scope judgment: evidence is locally editable and is not a cryptographic attestation. A writer able to replace every receipt can forge internally consistent evidence. Contradictions detectable within one receipt should still be rejected, while ignored-input semantics and trust boundaries must be stated accurately.

Python 3.10 was not installed. The panel's compatibility evidence consists of Python 3.10 grammar parsing and selected Python 3.11 runtime checks, with other probes on Python 3.14/macOS. It does not establish Windows behavior or a real Python 3.10 execution result. The source changed during the panel; the mutation worker reran its nine controls against the newer source snapshot. Other results must be rerun after relevant fixes or retained as historical diagnostic evidence. Reports are preserved in `projects-testing.json`, `projects-testing-resumed.json`, and `projects-testing-report.md`, with hashes and count limits in `projects-testing-summary.json`.
