# Confidence Protocol source analysis and independent proof design

Date: 2026-10-12. Scope: the repository's existing Confidence Protocol CLI, schemas, references, and tests. This report records design before implementation; line references below describe the pre-change source. Vendor/harness capability research is owned by the other research panels.

## Recommendation

Add optional obligation dependency declarations, a deterministic read-only `next --json` work frontier, and contract-pinned structured review provenance. Keep the existing capture engine and schema versions backward compatible. This improves task decomposition, prioritization, and auditable review without pretending that command success proves a semantic claim or that a new model name confers reliability.

A newer harness can execute a larger plan, but readiness must still depend on valid proof at the prerequisite boundary. The CLI should identify remaining obligations and explain dependency blockers; the existing agent/harness remains responsible for choosing and executing verification. It must not execute free-text verification instructions automatically.

## Minimal extension contract

### Dependency graph

Each obligation may include `depends_on`, a list of exact obligation IDs. Omitted or empty means no prerequisites and preserves legacy behavior. Reject non-lists, non-string/blank IDs, duplicates, unknown IDs, self-dependencies, and cycles. Use an iterative graph traversal so a long valid chain does not crash at Python's recursion limit. Do not impose arbitrary graph-size restrictions without a defined resource contract.

A prerequisite is satisfied only when its result is pass and its supporting evidence remains valid. Transitive prerequisites matter: validating only the direct status permits a manually promoted intermediate claim to enable its descendants. The contract may contain unrelated unfinished obligations; incremental `record --status pass` should validate only the selected obligation and ancestor closure, preserving all other fields. Recording partial/fail/not_run must remain possible even when prerequisites are incomplete.

Ordinary whole-report validation should detect a declared dependent pass with a non-pass prerequisite, preserving the distinction between a structurally valid partial report and a false claim of prerequisite completion. Captured runs can support multiple claims if their actual coverage warrants it; graph edges do not create independent proof.

### Read-only frontier

`next --json` should load strict JSON, validate the full contract before deriving relationships, validate supporting evidence, and return deterministic obligation IDs/claims/verification with ready/blocked/completed distinctions and explicit reasons. Contract order is a sufficient ordering rule; a numeric priority system is unnecessary.

A stale or tampered pass cannot enable a dependent. Safest initial behavior is an invalid result with errors and no ready frontier, leaving the agent to repair invalid evidence; more permissive per-obligation error handling needs separate proof against downstream false readiness. Do not execute shell commands or verification text. Do not write telemetry, reports, locks, caches, or generated receipts. Omit random operation IDs and current timestamps from deterministic output. The read-only property includes missing-directory and error/crash paths.

Read-only planning is not immutable observation. Concurrent manual changes may occur after final validation. Output is an advisory current observation; mutation remains subject to normal locked recording and validation.

### Structured review provenance

Preserve existing contract v1/report v3 readers and legacy completion semantics. Add optional contract-pinned requirements, for example `review_policy.records_required`; presence of report records alone is too easy to remove accidentally and should not be the only enforcement switch. New Critical templates may opt in, but silently invalidating every old Critical report without a schema migration is not justified.

Each structured record should identify its role, reviewer identity, origin/harness, scoped obligation IDs, findings, resolvable reference, and declared independence. Coverage of a role is earned by a record, not by adding its name to `review.roles`. Required records must cover required roles. Critical test-design and adversarial review should be attributable to distinct reviewers; shared model family does not by itself prove dependence or independence. A record of unresolved blocking findings must not count as approval.

This is auditable declared provenance. It cannot authenticate a reviewer, establish actual independence, prove that the reference was read, prevent a writer from forging every field, or prove semantic review quality. Do not introduce a false security guarantee. A model/harness/version can supplement origin; it cannot replace narrow scope and raw evidence.

## Bounded autonomous operation

The agent should iterate: inspect the frontier, choose a ready obligation, perform the smallest meaningful action, capture proof, inspect its coverage, explicitly record the judgment, and inspect again. A repair should follow a concrete counterexample and invalidate affected proof. Stop/reassess on repeated failure with no new evidence, exhausted authorized budget, unavailable required boundary, or unresolved consequential choice. The CLI should report the gap rather than manufacture progress. The current timeout, capture cancellation, durable run records, and resume behavior remain the execution foundation.

No new model-specific launcher, voting ensemble, automatic confidence percentage, or free-text command interpreter is needed. Model/harness evolution changes available execution affordances, not the logical requirements for a supported claim.

## Accepted implementation refinements

The implementation owner accepted the proof design and selected strict full-report frontier validation: invalid/stale evidence returns no ready obligations. The deterministic JSON shape is `{ok, ready, blocked, complete, completion_errors}`; invalid input returns `{ok:false, errors, ready:[], blocked:[], complete:false}` with exit 1. Ready and blocked IDs follow contract order. A blocked entry lists incomplete direct prerequisites; full report validation prevents a transitive invalid pass from being treated as ready.

The implementation additionally invalidates transitive passed descendants when an upstream result's status or supporting run IDs change. Descendants become partial, retain their historical references, and receive an explanatory detail. This avoids silently treating old downstream proof as current after its prerequisite proof changed. A details-only edit leaves support identity unchanged and does not trigger demotion. This is a conservative logical invalidation rule, not a semantic claim that every changed upstream description is harmless.

Add to the pre-implementation matrix: chain and diamond invalidation; replacing supporting runs while remaining pass; pass-to-partial; no demotion for details-only changes; unchanged repeat idempotence; unknown report extensions retained; malformed descendants refuse mutation rather than losing evidence; report bytes unchanged on unsatisfied prerequisite rejection. The dependent pass operation validates the actual selected prerequisite closure with existing evidence readers/source validation; unrelated unfinished narrative fields stay allowed.

Direct baseline observations were saved before the change in `.confidence/research/protocol-baseline-proof.json`: an unknown dependency declaration was ignored by contract validation, and Critical role names without identities/origin satisfied the legacy completion helper. These function-level controls characterize the existing schema; they do not claim a semantic review occurred or prove malicious authentication resistance.

## Research panel comparison and decisions

All eight research reports were read, compared with the source, and used to challenge the minimal design. Dependency, provenance, schema, and smallest-change researchers independently corroborated the single-obligation scratch-contract trap, role-name provenance gap, deterministic output requirement, and the risk of new arbitrary evidence files invalidating captures. The evidence-freshness researcher found no supported case of a persistently changed Git-bound source silently passing current validation. That is a reason to preserve the capture engine rather than rewrite it.

The native coordinator proposed advisory-only dependencies and unchanged completion rules, chiefly to preserve older tools' behavior. The implementation chooses stronger semantics when users declare dependencies: dependent pass requires actual upstream proof, and upstream proof changes demote transitive passed descendants. Old contracts omitting dependencies retain their behavior. This is a deliberate correctness choice; older CLI versions ignore the added fields, so a consumer requiring their enforcement must use the updated tool.

The panel preferred a richer per-obligation frontier usable on invalid initial reports. The initial implementation instead refuses an invalid/stale full report with no ready work. This smaller surface gives a clear invariant: every emitted ready frontier follows full evidence validation. The limitation is that agents must complete required narrative/schema fields and repair stale evidence before receiving a frontier. Returning readiness despite invalid evidence would need a separate proof design.

The coordinator proposed report v4 before stronger provenance completion gates. Contract-pinned opt-in enforcement offers a narrower compatible route: existing report-v3 documents keep legacy semantics unless their contract explicitly requires records. Reviewer identity, model, harness, independence and semantic approval remain declarations; hashes bind the local referenced bytes, not the author's truth. Captured native CLI metadata can corroborate aggregate usage, but model self-description is not independent attestation.

Do not widen generated-file fingerprint exclusions to accommodate transcripts. Prefer already owned `runs/*.log` references or create the final review artifact before capture; an ignored task directory is also outside the Git inventory by definition. Review file edits must cause hash mismatch. Git metadata, external dependencies, ignored files, empty directories and environment-specific ignore rules remain separate proof boundaries.

The bounded-progress researcher proposed fixed retry numbers (20 attempts/5 seconds and three identical failures). These are uncalibrated policy suggestions, not measured reliability thresholds. Retain concrete progress criteria, authorized budgets, and explicit blocker reporting; avoid presenting a magic count as a guarantee. The experiment researcher correctly identified inherited Git/telemetry environment as a fixture hazard. New frontier tests sanitize those variables without changing the user's home directory; a local telemetry observer tests that read-only planning sends no requests even when telemetry is enabled.

## Executed protocol boundary tests

The independently authored `skills/confidence-protocol/tests/test_dependency_frontier.py` now contains 24 public CLI tests. They use real disposable Git repositories and real `run` captures, not mocked source freshness. The focused suite was run with `python3 -B -m unittest discover -s skills/confidence-protocol/tests -p 'test_dependency_frontier.py' -v` and passed after implementation fixes. The final PR proof must still capture the full suite against the final source state; this focused observation is not a substitute for that receipt.

The tests exercise: deterministic contract-order roots/blockers; byte-identical repeated output and unchanged filesystem inventory; missing-directory refusal without creation; no verification-text shell execution; malformed dependencies, unknown/self/duplicate edges and cycles; a 1,500-obligation chain beyond typical Python recursion depth; legacy contracts; rejected dependent pass preserving report bytes; selected-closure pass with unrelated unfinished narrative retained; blocked partial recording; fresh dependent support unable to hide stale upstream proof; tampered upstream log refusal; chain/diamond transitive demotion with historical run references retained; supporting-run replacement versus details-only edits; empty frontier with incomplete release gates; malformed passed-descendant refusal; unhashable evidence IDs; deeply nested JSON; FIFO/symlink document readers; and enabled local remote-telemetry observation with zero POSTs on success and refusal.

Two malformed-input counterexamples were sent to the implementation owner while tests were being authored: a missing/non-string descendant detail could raise during demotion, and deeply nested JSON could escape as `RecursionError`. Both are now covered by public regressions and passed in the focused run. Fixture environments remove inherited Git-routing and telemetry variables and disable global/system Git configuration. Diagnostics are left enabled for the read-only tests so the absence of writes is a meaningful assertion.

The parent receipt has an empty permission-denial list, but child summaries report denied compound `cd && python3` commands, heredocs, and some multiline scripts. Children repaired to absolute test paths and allowed `python3 -c` calls. One read-only reviewer claimed a compound command ran despite other reviewers' denials; that particular claimed focused-test result is unconfirmed. Direct independently executed regression tests establish the relevant boundary instead. A graph reviewer's first probe had its own directory-reading error and was repaired. A scalability reviewer's first script had a syntax error before execution and was repaired. Attempted commands are not counted as executed proof.

Three material counterexamples were independently reproduced before fixes:

1. **Git fsmonitor violates read-only planning.** A repository configured with a filesystem-monitor program invoked that program twice during `next`, which returned `ok:true`; the program wrote an ignored sentinel. Read-only Git inspection can execute repository configuration, even when verification text is never interpreted. The implementation now disables `core.fsmonitor` for its inspection commands. A real executable hook/sentinel regression checks that it stays uninvoked.
2. **Malformed legacy start metadata crashed JSON planning.** A research run changed to version 1 with `workspace_start:"x"` produced an `AttributeError`, empty JSON stdout, and a traceback. Version 1 never owned that field; the corrected validator ignores its unknown extension instead of interpreting it as version-2 provenance. Regression variants include string, list, integer, and boolean extensions and preserve valid legacy research semantics. Software version-1 records still cannot supply current start-state provenance.
3. **Deep JSON crashes ordinary validation/recording.** The initial 1,500-level case was insufficient on Python 3.14: its decoder accepted that depth and later rejected ordinary report fields. The exact two-megabyte/one-million-level valid JSON input produced structured refusal from `next` but generic internal-error exit 125 from `validate` and `record`. The reader now converts decoder `RecursionError` into a path-qualified `ValueError`; regressions require normal input-error refusal (`next`:1, `validate`:2, `record`:2), avoiding the crash path. No claim of a general JSON size/storage bound is made.

Independent reproduction artifacts are `.confidence/research/protocol-test-reproductions.json` and `protocol-deep-json-reproduction.json`. They record current observations, not immutable execution snapshots, while the implementation owner was applying fixes. The final suite must establish the repaired behavior against its final source binding.

Remaining panel reports were classified proportionally. Duplicate prerequisite errors and needless demotion after run-list reordering are quality/efficiency issues rather than false acceptance. Different report-array ordering is a different input; stable-input byte determinism was confirmed across hash seeds, but no canonical-semantic-equivalence guarantee is promised. Multi-repository proof scopes are supported and must remain explicit; a report does not certify an unobserved caller checkout. `init --resume` intentionally recovers identity without full validation, and a later `next` must still reject a cyclic graph. Manually replacing both a record and its log remains forgery within the documented trust limit. Unicode text output, oversized files, and concurrent mutation between validation and scope rendering remain separate follow-up boundaries, not evidence that the checked frontier accepts stale proof.

The child panel reported single-run stress observations of a 20,000-node chain and a 2,000-node/~two-million-edge dense graph under one second, and a 3,000-node dependent record/demotion exercise. These timings are child-reported observations from one machine, not reproducible performance guarantees. The checked-in 1,500-node public-CLI regression directly proves recursion-safe graph traversal. Concurrent-writer behavior, cross-platform timing, semantic independence, and actual reductions in human intervention still require their appropriate existing tests or controlled task trials.
