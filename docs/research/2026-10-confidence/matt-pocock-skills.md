## Candidate mechanisms

### M1. Prove diagnostic sensitivity before trusting a forced-red run

Upstream requires an executed symptom-specific command and, when red is forced by a mutation, a diff against pristine source to establish that the mutation landed. It also repeats the original scenario after the minimized regression passes. [skills/engineering/diagnosing-bugs/SKILL.md:57–66](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/diagnosing-bugs/SKILL.md#L57-L66) [skills/engineering/diagnosing-bugs/SKILL.md:114–128](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/diagnosing-bugs/SKILL.md#L114-L128)

CP already requires reproduction before repair, disprovable checks, retained diagnostics and affected reruns. Mutation-landing confirmation and explicit original-versus-minimized scenario pairing sharpen that guidance. When a test sensitivity check mutates source or fixtures, retain the exact disposable mutation diff and show that it reached the intended path. Pair minimized regression evidence with the original triggering scenario where reduction could discard relevant context.

**Proposed acceptance/counterexample check:** In a future separate evaluation, deliberately make the mutation a no-op or target the wrong fixture. The route must reject it as sensitivity evidence. Also test a minimal regression passing while the original multi-caller scenario still fails. A fixture change that merely causes setup failure is not the reported bug. Non-deterministic behavior may require bounded repeated observations, not a binary guarantee. These are future evaluation proposals, not executed trials.

### M2. Describe each verification boundary and its misses; use independent expected outcomes

Upstream names the tested public seam, pairs proposed seams with catches/misses, and rejects expected values calculated by the implementation algorithm. [skills/engineering/tdd/SKILL.md:18–32](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/tdd/SKILL.md#L18-L32) [skills/engineering/tdd/tests.md:63–76](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/tdd/tests.md#L63-L76)

CP already requires public behavior, readable literal failures, non-duplicative coverage and real external-contract checks. A catches/misses note and independent expected-value origin are useful concrete prompts. For consequential checks, identify the observed interface, the important behavior it can reject, and relevant boundaries it misses. Derive expected results from a spec, worked example or trusted independent oracle. Reuse existing task authorization rather than adding seam confirmation.

**Proposed acceptance/counterexample check:** Use cases where a mock returns success without writing to storage, where tests recompute a faulty total, and where internal refactoring preserves behavior. Candidate guidance must retain the external gap, reject tautological expected values, and preserve refactor-stable tests. A highest-level UI test can omit a transactional invariant; a direct database assertion can be appropriate for a storage contract. Do not import a universal ban on lower-level checks or require one seam. These are future evaluation proposals, not executed trials.

### M3. Keep requirement coverage distinct from discretionary standards findings

Upstream separates Standards and Spec review: the former distinguishes documented rules from smell heuristics and skips mechanically enforced rules; the latter names missing/partial requirements, scope creep and wrong implementation with spec citations. [skills/engineering/code-review/SKILL.md:34–41](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/code-review/SKILL.md#L34-L41) [skills/engineering/code-review/SKILL.md:62–89](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/code-review/SKILL.md#L62-L89)

CP already has simplicity judgment, independent consequential review, Critical test-design/adversarial roles and attributable scoped review records. Two categories can make a review more inspectable; they do not replace required roles or their evidence. Ask reviewers to enumerate requirement gaps separately from maintainability recommendations. Cite the requirement and source hunk for a product defect; identify a smell as judgment and defer to repository standards. Retain both signals without letting numerous style suggestions mask one behavioral failure.

**Proposed acceptance/counterexample check:** Present a standards-clean diff that omits one required authorization check and a behavior-correct diff with one discretionary smell. The first must remain incomplete; the second must not be falsely promoted to a product defect by the smell. Absence of a formal spec does not justify skipping review of user intent or proof obligations. Native owner must verify alleged defects, and separate headings alone do not establish independent review. These are future evaluation proposals, not executed trials.

### M4. Handle wide refactors with explicit expand, migrate and contract guarantees

Upstream recommends self-verifiable vertical slices, with an explicit exception for a mechanical change spanning many callers: expand both forms, migrate batches, then contract after all batches. If only integration can be green, a final integrate-and-verify ticket owns that guarantee. [skills/engineering/to-tickets/SKILL.md:25–40](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/to-tickets/SKILL.md#L25-L40) [skills/engineering/implement-spec/SKILL.md:13–36](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/implement-spec/SKILL.md#L13-L36)

CP already has dependency DAGs, readiness frontiers, descendant demotion, isolated ownership and verification after integration. Expand–contract supplies a useful plan shape for broad refactors without changing those gates. When independent vertical slices cannot stay compatible, state old/new compatibility obligations and blocker edges. Never claim batch-level green behavior that only final integrated proof establishes. Preserve authority over branch operations and external issue changes.

**Proposed acceptance/counterexample check:** Create a future disposable refactor case with an unmigrated caller and a batch that works alone but conflicts after merge. The plan must block contraction and final completion until complete caller search and integrated behavior pass. A trivial rename does not warrant elaborate migration scaffolding. Coexistence can itself introduce unsafe writes; expansion requires real compatibility proof, not just two symbol names. These are future evaluation proposals, not executed trials.

### M5. Use architectural removal and locality questions as optional review heuristics

Upstream evaluates whether removing a module disperses useful behavior into callers or merely removes indirection, prioritizes recently changing areas, and compares interface alternatives under different constraints. [skills/engineering/codebase-design/SKILL.md:60–65](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/codebase-design/SKILL.md#L60-L65) [skills/engineering/improve-codebase-architecture/SKILL.md:20–35](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/improve-codebase-architecture/SKILL.md#L20-L35) [skills/engineering/codebase-design/DESIGN-IT-TWICE.md:19–38](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/codebase-design/DESIGN-IT-TWICE.md#L19-L38)

CP already prefers a single rule owner, justified abstractions and removal of unused scaffolding. The removal thought experiment and recent-change locality provide concrete questions, not a new architecture gate. For a consequential abstraction decision, compare a direct implementation with an alternative against actual callers, error modes and change locality. Use recent friction to choose scope. Preserve required trust/persistence adapters even if they look thin.

**Proposed acceptance/counterexample check:** Use one redundant pass-through and one small adapter that carries authorization or error normalization. The route should remove or justify the first without deleting the second merely because its implementation is short. Exactly two adapters is not a universal prerequisite for a valuable interface; a stable single adapter can enforce a consequential contract. Hotspots also miss new or rarely changed critical code. These are future evaluation proposals, not executed trials.

### M6. Check documentation triggers and keep essential decisions beside their caveats

Upstream treats description/reference wording as a trigger, splits branch-specific reference from common steps, co-locates caveats, sharpens observable completion and tests alleged no-op instructions against actual model behavior. Its router requires reading the actual skill before recommending it. [skills/productivity/writing-for-agents/SKILL.md:10–43](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/writing-for-agents/SKILL.md#L10-L43) [skills/productivity/writing-for-agents/SKILL.md:45–52](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/writing-for-agents/SKILL.md#L45-L52) [skills/productivity/writing-for-agents/SKILL.md:76–81](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/writing-for-agents/SKILL.md#L76-L81) [skills/engineering/ask-matt/SKILL.md:9–11](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/ask-matt/SKILL.md#L9-L11)

CP already uses progressive references and concrete evidence/completion rules. Trigger-specific selection and a source-read prerequisite can sharpen documentation review. Assertions about prompt effects or token reduction remain unverified here. For each required reference, name the cases that trigger loading and retain any always-needed authority or proof caveat in core context. Before removing a supposedly redundant rule, identify an observed default and test whether removal changes a representative behavior in a separately authorized evaluation.

**Proposed acceptance/counterexample check:** In a future separate evaluation, supply a task touching persistence, a direct Quick edit and an interrupted cross-provider handoff. Required reference/authority rules must remain reachable while irrelevant references stay unloaded. Include a catalog summary that contradicts an entry file; the entry must win. Splitting a document can hide a needed guardrail. Frontmatter and slash-command reach differ by host; source advice is not runtime qualification. Do not import a numeric context threshold or claims that phrasing universally improves accuracy. These are future evaluation proposals, not executed trials.

## Already covered, conflicts and omissions

Confidence Protocol already covers task contracts, public-behavior checks, expected pre-fix diagnostics, realistic external boundaries, logical dependency frontiers, edit ownership, integration before proof, escalating failed routes, source-bound receipts, attributable independent review, compaction recovery and proportional cost accounting. Upstream context pointers, parallel ticket execution, primary-source research and portable handoffs mainly corroborate existing guidance. The [handoff entry](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/handoff/SKILL.md#L8-L16) adds sparse artifact pointers and focus, but does not replace CP’s durable authority, review provenance and receipt reconciliation.

Several source rules conflict with autonomous work already authorized by a user. [`tdd`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/tdd/SKILL.md#L22-L24) prohibits tests before user-confirmed seams; [`to-spec`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/to-spec/SKILL.md#L15-L19) asks for seam confirmation; [`to-tickets`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/to-tickets/SKILL.md#L42-L60) iterates until breakdown approval; [`grilling`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/productivity/grilling/SKILL.md#L26-L30) reserves every decision to the human. Those are appropriate to an explicitly chosen interview workflow, but should not become mandatory CP pauses for routine implementation choices. [`implement`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/implement/SKILL.md#L13-L17) commits automatically, and [`implement-spec`](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/implement-spec/SKILL.md#L25-L40) manages branches, draft PRs, issue closure and cleanup. Such actions must retain their actual task authorization. A research skill does not grant external messaging authority.

Other policies need adaptation rather than copying: default full-suite runs are not proportional verification; refactoring exclusively after red-green cycles is not a universal timing rule; insisting on one highest seam can miss storage or trust invariants; deleting shallow-module tests needs coverage evidence; a count of adapters is not proof of a useful abstraction. A review of `HEAD` against a fixed Git point does not cover uncommitted changes automatically. Explicitly choose the intended change scope rather than blindly importing the upstream command.

The released entries provide prompt-level workflow rules, not mechanical proof that tests ran, artifacts bind current source, prerequisite passes remain valid, published actions were reconciled after interruption, or review identities are authentic. They omit CP’s source-binding/completion gates and detailed model/usage/permission receipts. The source assigns recursive-subagent containment to the [harness](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/.out-of-scope/subagent-recursion.md), reinforcing the need to qualify actual runtime behavior rather than rely on a prose instruction. Upstream “smart zone” thresholds, claims about phrasing and contextual load, and advertised token reductions were not validated here.
